# Spec: Setup B — Local application setup

Status: Complete on 2026-09-16. The local health flow, locked dependencies, and disposable database check were implemented and verified; hosting and product behavior remain later work.

## Overview

Create the smallest runnable local application slice: a Next.js desktop page calls a FastAPI health endpoint and shows whether the backend is reachable. Establish a disposable local Supabase PostgreSQL test workflow for later specs. Setup B makes the proposed frontend/backend split executable without introducing catalog, recommendation, account, or public deployment behavior. It follows completed Setup A; Setup C verifies hosting and public OAuth prerequisites, and Spec 01 introduces stored dish cards.

## Depends on

- Setup A — Validate catalog and decide the first experience: complete. Its product decisions and factual sample remain evidence, not a database seed for this task.
- No numbered feature spec. The implementation must not depend on Setup C, authentication, a catalog migration, or a hosted database.

## User flow

1. An operator starts the local backend and frontend using documented commands. The page identifies the application as a local setup view and displays a successful API connection when FastAPI answers.
2. If the API is stopped, unreachable, or returns an unexpected response, the page displays a clear unavailable state. A later successful check can return the page to the healthy state without a rebuild.
3. The page has no dish, recommendation, sign-in, or public-product flow. It must be readable and keyboard usable at the roadmap's representative desktop sizes, 1280×800 and 1440×900.

## Routes / API endpoints

| Method | Path | Purpose | Access |
|---|---|---|---|
| `GET` | `/health` | Return a small, stable success response, for example `{ "status": "ok" }`, when the FastAPI process can serve requests. This is a process check, not a claim that Supabase, OAuth, or catalog features work. | Local unauthenticated check in Setup B; Setup C reviews its public exposure. |

The local frontend calls the backend URL from a documented environment variable. Configure CORS for the exact local frontend origin used by the workflow; do not use an unrestricted production origin. No other API route is introduced.

## UI / Components

- Create the minimal Next.js App Router page and layout with React, TypeScript, and Tailwind. Show an initial checking state, a healthy state, and a backend unavailable/error state. Treat malformed/non-success API responses as unavailable.
- Keep text honest: the connection check does not imply the catalog, recommendations, sign-in, or public deployment is ready. No navigation or reusable product components are needed yet.
- Use a short request timeout or equivalent bounded failure behavior so an unavailable API does not leave the page checking indefinitely. A reload or explicit retry should recheck the API.

## Rules for implementation

- Explain the local process and configuration choices before writing application code. Keep frontend and backend in separate roots, with local ingestion/enrichment reserved for later operator work.
- Use one explicit browser-visible backend origin variable and restrict the local backend's CORS origin to the local frontend. Keep any future privileged credentials server-side; never put secrets in `NEXT_PUBLIC_` variables or Git.
- Keep `/health` cheap, bounded, and free of live provider or database calls. Do not add public data/request endpoints in this setup task. Shared request limits are required before later public data/request endpoints are exposed.
- Use only the local disposable database for connection or destructive checks. A successful local database check must be shown separately from the health status.
- Treat the architecture's Vercel/Render choice and Google publication as pending Setup C checks. Historical references to public OAuth in old Setup B/Spec 08 records map to Setup C/Spec 12 under the roadmap migration guide.
